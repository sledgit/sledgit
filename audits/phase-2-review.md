`deploy/testnet`, `contracts/vault/examples`, `agent/src`, `agent/SKILL.md` and `agent/test/audit.test.ts`.
Ed25519 verification of the flagged attestation fields. No transactions were sent, no key file was read, and no repo

## Answers to the review questions

1. **On chain.** Matches the result files, except for the suite-vault keys (P2-2) and the factory float (P2-1).
   Holders of full-access keys are listed above. The root keeping a key gives it no power over `arena` or its vaults.
   The risk is that its key is the owner key (P2-5), and that provenance still trusts the root as a factory (P2-3).
2. **`deploy_and_lock`.** It fails closed: no key is deleted before every check passes, it deletes only the
   factory's own freshly generated key, it refuses an existing factory, and it never prints a secret. Weaknesses: the
   checks compare against the same constants used to initialise (P2-4), there is no float check (P2-1), no resume path
   (P2-6), and the network guard is indirect (P2-7). The mainnet list is in P2-4 and P2-7.
3. **`arena_setup` / `consolidate`.** Key files are 0600 in a 0700 directory, with a write-then-chmod nit (P2-8), and
   nothing secret is printed. The no-allowance policy is safe: a function-call key can't move NEAR, and the balance
   bounds gas burn. The function list is minimal: the five `assert_agent`/owner-or-agent methods plus
   `intents_settle`, which the agent needs to sign. The docs omit the in-policy trading, freeze-griefing and
   record-pollution impact (P2-10).
4. **Secrets.** None (P2-15 false positives only).
5. **`vault.ts` / `SKILL.md`.** Correct. P2-11 to P2-13 are consistency nits, and P2-10 is the doc gap.
